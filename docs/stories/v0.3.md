# v0.3 Android: stories

The stories for [v0.3 Android](../../ROADMAP.md#v03-android), grouped by epic in the order they are built. Each story is a vertical slice that can be tested on its own. Product rules come from [RANTAKIT.md](../../RANTAKIT.md), words from [GLOSSARY.md](../../GLOSSARY.md), and code boundaries from [ARCHITECTURE.md](../../ARCHITECTURE.md).

Every story has acceptance criteria, the layers it touches, the screens and states it needs designed, and its platforms. v0.3 brings the v0.2 Tools to Android, so every story below is **Platforms: Android** unless it says otherwise.

Decisions made while writing these stories (2026-11-03):

- One tag, `v0.3.0`, releases Windows, Linux, and Android. Desktop keeps the v0.2 Tools and gains "Versi baru" (New version, U1).
- Two APKs, one per ABI: `Rantakit_<version>_arm64.apk` (listed first, for almost every phone since 2017) and `Rantakit_<version>_armv7.apk`. They are signed with one release keystore that the maintainer keeps and backs up, stored as GitHub secrets.
- The Android back gesture follows the same steps as Back on desktop (W2 in v0.2); on Home with no step left, the app closes.
- On a phone, Settings is a full page, and the Result is its own screen. Going back from the Result closes the Tool.
- Results always go to `Download/Rantakit/` on Android, so the "File hasil" (Result files) part of Settings is hidden there, and the Result offers Open and Share, without Show in folder.
- Share → Rantakit, "Buka" (Open), and a desktop drop are one file-first flow.
- Photos are chosen with the system file picker, not the Photo Picker, because the Photo Picker hides file names and Results are named after their Original (2026-11-04).
- Every Task runs in a foreground service with a progress notification, so a Task with many files survives the user switching apps. The permissions it needs are asked for once, with a reason.
- The APK from GitHub checks for a new version and opens the download page; it never installs one itself. Store builds will leave the check out.
- Android needs an up-to-date Android System WebView (Chrome 111 or later); an older one gets a message on how to update it (A1).
- Speed is measured on an emulator for now (Android 8.0, 3 GB RAM) and recorded as an estimate; the check on a real low-end phone moves to the beta before 1.0, with the usability test.

## 1. Android build

### A1. Rantakit runs on Android

**Capability:** the four v0.2 Tools run on Android 8.0 and later, from the same engines and product rules as desktop ([ADR 0004](../adr/0004-engines-and-tasks-in-tauri-free-crates.md)).

**Acceptance criteria**
- `src-tauri/gen/android` is generated and committed; the app builds for arm64-v8a and armeabi-v7a with `minSdkVersion` 26 (Android 8.0).
- Kompres Foto, Ubah Format Foto, Ubah Ukuran Foto, and Kompres PDF (compress photo, convert photo, resize photo, compress PDF) give the same Results as on desktop for the same files and options. Resized photos may differ in a few bytes, because the Lanczos filter uses the system's math library, which rounds differently on each platform; the difference cannot be seen.
- Home shows the same Tools; among the coming soon cards, "Scan Dokumen" (Scan document) appears only on Android (H2 in v0.2).
- The window controls, title bar, and keyboard shortcuts are not part of the Android app.
- Rantakit needs Android System WebView 111 or later (2023), which Android 8 and later get from the Play Store. An older WebView, such as the one an Android 8 phone ships with, shows "Rantakit perlu WebView yang lebih baru" (Rantakit needs a newer WebView), how to update it, and "Buka Play Store" (Open Play Store), instead of a blank screen.
- Each APK fits the size budget for its ABI ([ADR 0009](../adr/0009-size-budget.md)): 20 MB for arm64, 16 MB for armv7.

**Layers:** `src-tauri`, `src-tauri/gen/android`, frontend (platform checks)
**Screens and states:** none

### A2. Signed APKs on every release

**Capability:** each release tag publishes two APKs that install over the previous version without losing data.

**Acceptance criteria**
- The release workflow builds both APKs in the same draft release as the desktop files (one draft per tag, from issue #7).
- Both are signed with the release keystore from GitHub secrets; a build without it fails instead of publishing an unsigned APK.
- The files are named `Rantakit_<version>_arm64.apk` and `Rantakit_<version>_armv7.apk`; the install table in the release notes lists arm64 first, with a line on how to tell the two apart.
- Installing a newer APK over an older one keeps History, Presets, and Settings.

**Layers:** `.github/workflows`, `src-tauri/gen/android`
**Screens and states:** none

### A3. Android in CI

**Capability:** code that doesn't compile for Android is caught on the pull request, without a full APK build.

**Acceptance criteria**
- Every push and pull request runs `cargo check` for `aarch64-linux-android` and `armv7-linux-androideabi`, next to the existing Windows and Linux jobs.
- The full APK build runs only in the release workflow.

**Layers:** `.github/workflows`
**Screens and states:** none

### A4. Speed on a low-end phone

**Capability:** the performance bar is measured, not assumed.

**Acceptance criteria**
- Compressing a 10-page scanned PDF takes under 5 seconds on an Android 8.0 emulator with 3 GB of RAM, measured with a generated fixture and recorded in the story's pull request as an estimate.
- The measurement on a real ~3 GB phone is done on the beta before 1.0 (ROADMAP.md, v0.8).

**Layers:** `rantakit-pdf`, `rantakit-image`
**Screens and states:** none

## 2. Phone layout

### P1. Tool page on a phone

As a phone user, I see my files, the options, and the main button without hunting for them.

**Acceptance criteria**
- The Tool page is one column: the header, the files, then the options, with the main button ("Kompres" (Compress)) fixed at the bottom above the system navigation.
- With no files yet, the file area shows "Pilih foto" (Choose photos) or "Pilih PDF" (Choose PDFs) instead of the desktop drop zone text.
- The header's back button closes the Tool, asking first when files would be lost, like every other way out (L1 in v0.2).
- Working shows per-file progress with **Batal** (Cancel), as on desktop (L2 in v0.2).

**Layers:** frontend
**Screens and states:** Tool page on a phone (empty, with files, Advanced options open, working)

### P2. Result as its own screen

As a phone user, I see what I got and can use it right away.

**Acceptance criteria**
- When the Task finishes, the Result replaces the Tool page as its own screen, with the same rows, sizes, and messages as on desktop (L3 in v0.2).
- Actions: **Buka** (Open) opens the Result in the app the phone picks, and **Bagikan** (Share) opens the Android share sheet for one or all Results. There is no "Tampilkan di folder" (Show in folder).
- The summary says where the Results are: "Disimpan di Download/Rantakit" (Saved in Download/Rantakit).
- "Proses file lain" (Process another file) opens the same Tool empty. Going back from the Result closes the Tool and returns to the step before it, usually Home.

**Layers:** frontend, `src-tauri` (open and share on Android)
**Screens and states:** Result on a phone (all succeeded, some failed, one file, many files)

### P3. The back gesture

As a phone user, the back gesture takes me where I expect.

**Acceptance criteria**
- The Android back gesture and back button go one step back through the same steps as Back on desktop (W2 in v0.2): Home, History, and each Tool page.
- Leaving a Tool page this way asks first when files would be lost or a Task is running; staying keeps the steps as they were.
- An open dialog or sheet closes first, before any step is taken.
- On Home with no step left, the app closes, as Android apps do.

**Layers:** frontend, `src-tauri`
**Screens and states:** leave confirmation from the back gesture

### P4. Settings on a phone

As a phone user, I change settings on a screen that fits.

**Acceptance criteria**
- Settings ("Pengaturan") in the bottom bar opens a full page listing its parts: Appearance ("Tampilan"), Language ("Bahasa"), History ("Riwayat"), and About ("Tentang"). Each opens its own page, and back returns to the list.
- "File hasil" (Result files) is hidden on Android, since Results always go to `Download/Rantakit/`.
- Every change applies at once, as on desktop (ST1 in v0.2).

**Layers:** frontend
**Screens and states:** Settings list; each part as a page

### P5. Wide screens and turning the phone

As a tablet user, or with my phone turned sideways, I get the room the screen has.

**Acceptance criteria**
- The screen orientation is not locked.
- From 768 px wide, the app uses the wide layout (sidebar, files and options side by side), without the desktop title bar; below that, the phone layout with the bottom bar.
- Turning the phone keeps the files, options, and a running Task.

**Layers:** frontend
**Screens and states:** Tool page on a tablet

## 3. Files in and out

### F1. Choose files

As a phone user, I pick photos and PDFs the way my phone usually lets me.

**Acceptance criteria**
- Photos and PDFs are chosen with the system file picker, which needs no permission and can also browse other apps, such as Google Photos and Drive.
- Each chosen file keeps its real name, such as `ktp.jpg`, so its Result is `ktp (compressed).jpg`. The Android Photo Picker is not used because it hands over names like `1000000033.jpg`.
- Several files can be chosen at once, and Open ("Buka") offers both kinds, then the Tools that fit (H6 in v0.2).
- The chosen files are read through their `content://` addresses; nothing is copied before the Task runs.

**Layers:** `src-tauri`, frontend
**Screens and states:** none (system pickers)

### F2. Share → Rantakit

As a phone user, I send a photo or PDF from WhatsApp, Gallery, or Files straight into Rantakit.

**Acceptance criteria**
- Rantakit appears in the Android share sheet for one or several photos or PDFs.
- Shared files go through the same flow as Open and a desktop drop (H5, H6 in v0.2): the Tools that fit, or the reason none does with "Pilih file lain" (Choose other files).
- With a Tool page open and files not yet processed, the leave confirmation comes first; then the flow above.
- While a Task runs, the shared files are not taken, and the app says "Tunggu tugas yang sedang berjalan selesai dulu." (Wait for the running task to finish first.)
- Sharing into Rantakit works whether the app was closed, in the background, or already open.

**Layers:** Kotlin share plugin, `src-tauri`, frontend
**Screens and states:** matching Tools from a share; nothing fits; busy

### F3. Results in `Download/Rantakit/`

As a phone user, I find my Results in the Files and Gallery apps.

**Acceptance criteria**
- Every Result is written as a new file in `Download/Rantakit/`, with the names from RANTAKIT.md; the Original is never changed, and an existing file is never replaced.
- Photos show up in Gallery and every Result shows up in Files.
- On Android 8 and 9 the storage permission is asked for when the first Task starts, after one line of reason: "Supaya hasil bisa disimpan di folder Download." (So Results can be saved in the Download folder.) Android 10 and later never ask.
- If the permission is refused, the Task does not start, and a message says how to allow it in the phone's Settings.

**Layers:** `src-tauri` (`tauri-plugin-android-fs`), `rantakit-tasks`, frontend
**Screens and states:** storage permission reason; permission refused

## 4. Tasks in the background

### B1. A Task keeps going when I switch apps

As a phone user compressing many files, I can switch to WhatsApp and come back to a finished Task.

**Acceptance criteria**
- Every Task runs in an Android foreground service from the moment it starts until it finishes or is cancelled, whatever the number of files.
- While it runs, a notification shows the Tool and the progress, with a progress bar: "Kompres Foto · 3 dari 12 file" (Compress Photo · 3 of 12 files). Tapping it opens Rantakit on that Task.
- Cancel stays inside the app; the notification has no buttons.
- If Android stops the Task anyway, unfinished Results are removed and the Originals stay untouched.
- The service declares only the foreground service permissions its type needs, and the reason for each is written in ARCHITECTURE.md.

**Layers:** Kotlin service plugin, `src-tauri`, frontend
**Screens and states:** progress notification

### B2. Finished in the background

As a phone user, I know when my Results are ready.

**Acceptance criteria**
- If the Task finishes while Rantakit is in the background, the notification changes to "Selesai · 12 file hasil di Download/Rantakit" (Done · 12 Results in Download/Rantakit); some failed files are counted in it. Tapping it opens the Result.
- If Rantakit is on screen when the Task finishes, the notification goes away and the Result shows as usual.

**Layers:** Kotlin service plugin, `src-tauri`
**Screens and states:** done notification (all succeeded, some failed)

### B3. Asking to show notifications

As a phone user, I understand why Rantakit wants to show notifications.

**Acceptance criteria**
- On Android 13 and later, the first Task asks for the notification permission after one line of reason: "Supaya kamu bisa melihat kemajuan saat Rantakit ditinggal." (So you can see the progress while you're away from Rantakit.)
- It is asked only once. If refused, Tasks still run in the background; only the notification is hidden.
- Android 12 and earlier never ask.

**Layers:** frontend, `src-tauri`
**Screens and states:** notification permission reason

## 5. History on Android

### R1. History on a phone

As a phone user, I find a file I made earlier and use it again.

**Acceptance criteria**
- History works as on desktop (R1, R2 in v0.2), with Open and Share in place of Show in folder.
- A Result that was moved or deleted from `Download/Rantakit/` is marked as missing.

**Layers:** `rantakit-tasks`, `src-tauri`, frontend
**Screens and states:** History on a phone (empty, with entries, missing Result)

## 6. New version

### U1. New version on desktop

**Platforms:** Windows, Linux

Built in pull request #12, before these stories: at launch Rantakit checks the latest GitHub release, shows a "Versi baru" (New version) button in the title bar, and installs the update on Windows and the Linux AppImage. The `.deb` and `.rpm` open the download page. "Cek versi baru" (Check for new versions) in Settings, "Tentang" (About), turns it off. Only release candidates are pre-releases, so the check finds every final version.

### U2. New version for the APK from GitHub

As a phone user who installed Rantakit from GitHub, I hear about a new version without a store.

**Acceptance criteria**
- At launch, unless "Cek versi baru" is off, Rantakit reads the version in the latest release's `latest.json`. Nothing else is sent ([ADR 0001](../adr/0001-files-never-leave-the-device.md)).
- A newer version shows the New version button, whose dialog says what to do and opens the release page in the browser: "Unduh APK yang baru, lalu pasang. Riwayat dan pengaturanmu tetap ada." (Download the new APK, then install it. Your History and settings stay.)
- Rantakit never downloads or installs the APK itself, so it does not ask for `REQUEST_INSTALL_PACKAGES`.
- The "Cek versi baru" (Check for new versions) switch appears in Settings, About, on Android too.
- Builds for Google Play or F-Droid can be made without the check; which stores, and when, is decided later.

**Layers:** `src-tauri`, frontend
**Screens and states:** New version button on a phone; its dialog
